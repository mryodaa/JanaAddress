# Jana Address: питч, показ и ответы на вопросы

Документ для тех, кто защищает. Регламент: 3 минуты на презентацию и показ на ПК, затем 3 минуты вопросов. Жюри техническое, и что нужно сделать, уже написано в ТЗ (поля, API, UI, docker). Поэтому очевидное говорим одной фразой, а время тратим на то, **как устроено** и **чем мы сильнее**. На слайды уходит около 60 с, на показ около 2 минут.

Структура: 1) главные мысли, 2) как это работает (для понимания, не для произнесения), 3) тайминг, 4) слайды, 5) текст, 6) сценарий показа, 7) ответы на вопросы, 8) чек-лист перед выходом.

## 1. Пять мыслей, которые жюри должно унести

1. **Модель показывает, где поле, но не пишет значение.** Значение всегда буквальный срез исходной строки или каноническое имя из справочника, поэтому выдумать улицу невозможно по построению. Fuzz-тест на 60 тыс. мусорных строк: каждое значение есть в исходной строке.
2. **Свой справочник на 1,18 млн домов** из OpenStreetMap, КАТО и ручного ядра. Вся геометрия считается заранее, в рантайме только поиск по индексам SQLite.
3. **У каждого поля есть источник:** из строки, из справочника (дом / улица / полигон / точка / ориентир / КАТО / ядро) или правка оператора. Плюс trace по всем шагам разбора.
4. **Быстро и автономно:** 1000 адресов примерно за 3 с на ноутбуке, включая загрузку справочника и модели (лимит 5 мин); контейнер готов за 6 с (лимит 3 мин); образ собирается без сети.
5. **Честные цифры без train.json:** отложенные наборы, улицы, которых модель не видела, живые строки с data.egov.kz. Confidence — не придуманная формула, а вероятность ошибки, все веса подобраны по данным.

Все цифры в документе замерены 2026-10-17 на текущей сборке (`scripts/eval.py`, `training/fit_confidence.py`, CLI). Время контейнера — замер команды из README.

## 2. Как это работает (для выступающих)

Этот раздел не для чтения вслух. Он нужен, чтобы понимать, о чём говорите, и спокойно отвечать на вопросы.

### Путь одной строки

На вход приходит `{"id", "raw_address"}`. Строка проходит конвейер шагов (`src/jana_address/pipeline/`). Каждый шаг получает общее состояние разбора и дописывает в него поля, флаги и запись в trace.

| Шаг | Что делает |
|---|---|
| layout | строка набрана в английской раскладке («Fkvfns ek f,fz 150 rd 5»): перекодирует в русскую («Алматы ул абая 150 кв 5») |
| clean | убирает невидимые символы (U+200B, мягкий перенос, BOM) и лишние пробелы, при этом помнит соответствие символов исходной строке: значения потом режутся из **оригинала** |
| tokenize | делит на числа, слова и разделители; расклеивает слитное: «66квартал» → 66 + квартал, «47Бдом» → 47Б + дом. Дробь «55/6» и литера «12а» остаются одним номером. Телефоны, индексы и время («до 18:00») сразу помечаются как мусор |
| split_bilingual | в склейке «Актобе/Ақтөбе қаласы» помечает казахскую половину как дубль |
| parts | организации («ТОО «Сапа Трейд»») уходят в мусор; корпус/строение («11к2», «5 корп 2») забираются, чтобы номер корпуса не стал квартирой |
| admin | область, город, район по маркерам («г.», «обл», «р-н», «ауданы») и по справочнику |
| details | дом, квартира, подъезд, этаж по маркерам (кв, flat, kv, под., подьезд, эт…) |
| street | тип улицы (ул., пр-т, мкр, көшесі, даңғылы…) и название. Мкр без улицы → street_type «микрорайон», мкр + улица → living_area |
| landmark | ориентиры: предлоги (напротив, возле), объекты (магазин, ТЦ, школа), бренды (Magnum, Qazpost, Kaspi…) |
| numbers, building, leftover | дом и квартира по позиции, если маркеров нет («Абая 150-23» → дом 150, кв 23); корпус приклеивается к дому; село без маркера перед улицей |
| **tagger** | нейросеть размечает каждый символ: к какому полю он относится |
| **arbiter** | сравнивает разметку модели с полями правил и решает спорные поля |
| **reference** | заполняет из справочника **только пустые** поля: район, мкр, область, тип улицы |
| confidence | итоговая уверенность 0..1 |

### Правила

Все словари лежат в `src/jana_address/rules/*.yaml`: маркеры, типы улиц на русском, казахском и латинице, ориентиры, веса confidence. Новое написание добавляется строкой в YAML, код править не нужно.

### Модель (теггер)

Посимвольная **BiLSTM-CRF**. Каждый символ превращается в вектор, два слоя двунаправленной LSTM читают строку целиком слева направо и справа налево, а CRF выбирает согласованную последовательность меток (начало улицы, продолжение улицы, дом, мусор…).

* около 600 тыс. параметров, экспорт в ONNX с int8-квантованием: **650 КБ**; в рантайме нет torch, только onnxruntime и numpy;
* обучена **только на синтетике**: 150 тыс. строк из настоящих топонимов нашего справочника с искажениями, как пишут люди (слитно, латиница, опечатки, телефоны, ФИО, город в конце, без запятых, организации);
* 15% улиц и 10% населённых пунктов в обучение не попали: на них проверяем, что модель обобщает, а не запоминает (набор `unseen`).

**Почему модель не галлюцинирует.** Модель не генерирует текст, а только указывает границы куска строки. Значение поля всегда буквальный срез исходной строки (улица, дом, квартира) или каноническое имя из справочника (область).

### Арбитр (`pipeline/arbiter.py`, веса в `rules/arbiter.yaml`)

* Правила и модель выделили одно и то же: берём, уверенность выше.
* Разошлись: у каждого варианта считается счёт = априорное доверие + вероятность модели + проверки справочником (такой город есть? улица есть в этом городе? дом есть на этой улице?) + грамматика (этаж ≤ 40, подъезд ≤ 20, номер дома похож на номер).
* Спорные поля решаются вместе, перебором, так чтобы один символ не принадлежал двум полям.
* Правила дали null: модели нужно сильное подтверждение, потому что null лучше неверного значения.
* Веса подобраны логистической регрессией только на dev-наборах.

**Живой пример:** «Бесагаш Айтеке би, 68». Правила склеили село с улицей: улица «Бесагаш Айтеке би», города нет. Модель предложила город «Бесагаш» и улицу «Айтеке би». Справочник подтвердил, что село существует, улица Айтеке би есть именно в нём и дом 68 на ней тоже есть. Арбитр выбрал вариант модели (счёт 5,38 против 2,05), а район восстановился как Талгарский. Всё это видно в trace.

### Справочник

Собирается скриптами `scripts/build_reference/` один раз, с интернетом:

1. скачивается дамп OSM по Казахстану (Geofabrik) и классификатор КАТО (stat.gov.kz);
2. pyosmium вытаскивает границы, населённые пункты, мкр/ЖК, улицы, дома с номерами, объекты (магазины, школы, аптеки, почта);
3. shapely считает геометрию: в какой полигон района попадает каждый дом, какая доля улицы проходит по каждому району, к какому мкр относится дом;
4. результат — один файл `reference/reference.sqlite` (75 МБ) с готовыми привязками, без геометрии.

В рантайме только поиск по индексам: точно по алиасу → после нормализации (регистр, ё/е, казахские буквы, транслит латиницы) → нечёткий поиск rapidfuzz внутри найденного города.

Состав: 20 областей и городов респ. значения · 197 районов · 14 280 населённых пунктов (97% с районом) · 5 527 мкр/ЖК · 55 тыс. улиц · 1,18 млн домов · 34 тыс. объектов-ориентиров · 103 тыс. алиасов (рус/каз/лат/старые названия).

### Восстановление района: цепочка

1. Дом найден в справочнике → берём его район и мкр (`reference:osm:house`).
2. Дома нет → доминирующий район улицы (`reference:osm:street`). Если улица идёт через несколько районов, ставим лучшего кандидата с флагом и пониженной уверенностью.
3. Улицы нет → район по мкр, по селу (полигон OSM или КАТО), по однозначно найденному ориентиру.

Источник каждого поля возвращается при `?explain=true` и виден в UI: `string`, `reference:osm:house|street|polygon|point|poi`, `reference:kato`, `reference:seed`, `manual`.

### Confidence

Confidence — это вероятность того, что **все** поля метрики в записи верны. Считается логистической регрессией: `p = sigmoid(intercept + Σ вес × признак)`. Признаки: доля разобранной строки, есть ли улица/дом/город, худшая уверенность среди полей из строки, согласны ли правила и модель, флаги сомнений (неясная ориентация чисел, лишние числа, маркер без номера…), подтверждение справочником.

**Ни один вес не выставлен руками** (`training/fit_confidence.py`, результат в `rules/confidence.yaml`):

1. *Форма* — логистическая регрессия на 8000 размеченных синтетических dev-записей: какие признаки сильнее связаны с ошибкой. Самые сильные: согласие правил и модели (+1,29 / −1,29 к логиту), найдена улица (+1,59), найден город (+1,23), надёжность полей (+1,47).
2. *Уровень* — калибровка Платта на 389 живых dev-строках (llm_dev, egov_dev): на живых строках ошибок 1–2% записей, на синтетике больше, потому что в эталоне синтетики другое соглашение о написании города.
3. Флаги, которые на dev встретились меньше 30 раз, в модель не входят: вес 0, данных нет. Например «чинили раскладку» не встретился ни разу, поэтому на уверенность не влияет.

Качество калибровки на **отложенных** живых строках (ECE, меньше — лучше): llm_holdout 0,035 → **0,025**, egov_holdout 0,090 → **0,061** (до → после, старая ручная формула → по данным). На синтетике ECE хуже (0,07–0,13): уровень настроен на живые строки, а синтетика сложнее и с другим соглашением.

В UI «Из чего сложилась уверенность» показывает вклад каждого признака **в вероятность**, сумма вкладов равна итогу. Если вероятность выше 0,99, это видно отдельной строкой «Ограничение 0,99».

**Порог «неуверенных» 0,95** выбран по данным: на живых dev-строках на проверку уходит 13% записей, и в них 6 из 8 ошибок. Оператор смотрит каждую восьмую запись вместо всех.

### Гарантии

* `id` и `raw_address` возвращаются байт в байт, на каждую запись ровно один ответ, порядок сохраняется;
* исключение на одной записи → все поля null и confidence 0, батч не падает;
* нет модели или не хватило памяти → работаем на правилах;
* нет сети в рантайме, нет кэша по целой строке и сопоставления по id (проверяет тест `test_no_memorization`);
* fuzz: 60 тыс. мусорных строк (эмодзи, HTML, SQL, 10 тыс. символов, невидимые символы) без нарушений;
* вход в UTF-8, UTF-16 и cp1251 (файл из Excel не отклоняется).

### Стек

Python 3.12, FastAPI, SQLite, onnxruntime; фронт на React, Vite, TypeScript и Tailwind; Docker, образ собирается полностью без сети (зависимости в `vendor/wheels`). 390+ тестов, mypy strict.

## 6. Сценарий показа на ПК (1:50)

Все строки ниже проверены на текущей сборке. Результат указан, чтобы знать, на что показывать.

### Шаг 1. Скорость и API (0:15)

Терминал, Enter на заранее набранной команде:

```bash
time curl -s -X POST http://localhost:8000/api/v1/parse/batch -F file=@demo_1000.json -o out.json
```

> «Так жюри будет прогонять тест: батч-эндпоинт. Тысяча адресов — секунды при лимите пять минут. Форма ответа повторяет форму входа, на каждую запись ровно один ответ».

Называть вслух то время, которое покажет `time` на демо-ноутбуке. Замер CLI на ноутбуке команды: 1000 записей за 3,2 с вместе с первой загрузкой справочника и модели.

### Шаг 2. «Проверить строку» (0:45)

Разбор идёт на лету при вводе. Цвет в исходной строке = поле, клик по куску переводит к полю.

1. **Чип** `Нурсити 2 микрорайон 11дом 5 подьезд 239 кв` → микрорайон «Нурсити 2», дом 11, подъезд 5, кв 239; уверенность **86%**.
   > «Номер микрорайона не перепутан с домом, слитное "11дом" и опечатка "подьезд" разобраны. Уверенность 86%, ниже порога: модель кое-где не согласилась с правилами, и сервис честно отправляет запись на проверку оператору».
2. **Набрать руками** `Fkvfns ek f,fz 150 rd 5` → Алматы, улица «абая», дом 150, кв 5; **район Бостандыкский и мкр Гаухартас — из справочника, источник «OSM · дом»**.
   > «Строка набрана в английской раскладке, мы её узнали. Района и микрорайона в строке нет: дом 150 на Абая нашёлся в справочнике, оттуда его район и микрорайон. Бейдж "справ." — значит, этого нет в строке». Навести на бейдж источника.
3. **Набрать руками** `Бесагаш Айтеке би, 68` → город «Бесагаш», улица «Айтеке би», дом 68, Талгарский район, Алматинская область. Раскрыть «Шаги разбора», строка **«9b. Арбитр»**.
   > «Правила склеили село с улицей. Модель их разделила, а арбитр проверил по справочнику: улица Айтеке би есть именно в этом селе, дом 68 на ней есть, — и взял вариант модели. Каждое решение видно здесь».

Запасные примеры (чипы): `Туран 55/6 магазин береке 4подьезд 9этаж` (дом 55/6, ориентир «магазин береке», подъезд 4, этаж 9), `Турксибский район, Рыбинский переулок, дом 4` (город и область восстановлены по району), `Илийский район, Боралдай, ул. Ленина 1/2` (село без маркера, дробь в доме).

### Шаг 3. Пакет и ручная правка (0:40)

Вкладка с заранее загруженным пакетом.

> «Оператор загружает файл. Сверху сводка: сколько записей, сколько неуверенных, гистограмма confidence с порогом».

* `U` — только неуверенные;
* открыть запись, кликнуть по цветному куску исходной строки — фокус прыгает в поле; исправить значение;
* `Ctrl+Enter` — сохранено, следующая запись. «Правка помечается как "правка", исходное значение возвращается одним кликом»;
* «Экспорт JSON» — «на выходе формат жюри уже с правками оператора».

Горячие клавиши: `J`/`K` или стрелки — навигация, `U` — неуверенные, `/` — поиск, `Ctrl+Enter` — сохранить и дальше, `Esc` — закрыть, `?` — подсказка.

## 7. Вопросы жюри: короткие ответы

| Вопрос | Ответ |
|---|---|
| Почему не LLM? | Офлайн, около 2 мс на адрес, детерминизм, объяснимость. LLM исправила бы опечатки и падеж, а ТЗ требует «как в строке». Наша модель весит 650 КБ и не может выдумать значение. |
| На чём обучали модель, если train.json нет? | 150 тыс. синтетических строк из своего справочника с сильными искажениями (латиница, склейки, опечатки маркеров, телефоны, ФИО, организации). 15% улиц и 10% пунктов в обучение не попали: на них проверяем обобщение. |
| Как меряли качество? | `scripts/eval.py` повторяет метрику ТЗ (60/25/15, посимвольно после нижнего регистра и без пунктуации). Наборы: отложенная синтетика (на ней ничего не подбирали), unseen и «почти реальный» эталон: 607 строк «как пишет клиент» и 161 живая строка из data.egov.kz. Каждый набор поделён на dev и holdout, holdout прогнан один раз. |
| Почему hybrid ниже чистой модели на синтетике? | Модель обучена на том же генераторе, её цифра завышена. Арбитр консервативен: меняет решение правил, только когда это подтверждают справочник и грамматика. На живых строках так безопаснее. |
| Как считается confidence? | Это вероятность, что все поля метрики в записи верны. Логистическая регрессия по признакам разбора: форма подобрана на 8000 синтетических dev-записей, уровень — на 389 живых dev-строках. Ни одного веса руками. На живых отложенных строках ECE 0,025 и 0,061. |
| Почему порог «неуверенных» 0,95, а не 0,5? | Живые строки разбираются верно в 98–99% случаев, поэтому почти все вероятности высокие. Порог выбран по dev: на проверку уходит 13% записей, и в них 6 из 8 ошибок. |
| Почему «чинили раскладку» не снижает уверенность? | На dev-наборах такой строки не было ни разу. Флаги, по которым меньше 30 примеров, получают вес 0: влияние без данных мы не придумываем. |
| Почему на синтетике калибровка хуже? | Уровень настроен на живые строки. В синтетике ошибок больше, отчасти из-за другого соглашения о написании города в эталоне. Мы выбрали точность там, где данные похожи на данные жюри. |
| Как восстанавливается район? | Дом найден → его район (точка в полигоне на этапе сборки). Нет дома → доминирующий район улицы по доле домов или длины; доля < 0,8 → лучший кандидат с флагом и пониженной уверенностью. Дальше мкр → район, село → район области, ориентир → район. Источник виден в ответе и UI. |
| Не запоминание ли это? | Нет кэша по целой строке и сопоставления по id. В справочнике только топонимы, это проверяет отдельный тест `test_no_memorization`. |
| Что если модель упадёт? | Работаем на правилах, батч не падает. Исключение на одной записи → её поля null, confidence 0, остальные записи разбираются. |
| Слабые места? | Районы Караганды (в OSM нет полигонов), номерные улицы вне справочника («2-й проезд Рахимова»), сёла без маркера. Мы их знаем и меряем по тегам искажений. |
| Как добавить паттерн или обновить справочник? | Маркеры, типы улиц, ориентиры — YAML, без кода. Справочник пересобирается скриптами `scripts/build_reference/` из свежего дампа OSM и КАТО. |
| Город по-казахски, старая область? | Город и район отдаём как в строке (так требуют слайд 08 и посимвольное сравнение); казахская половина склейки через слэш отбрасывается. Прежняя область после передела 2022 года («ВКО, Семей») — как написано, без штрафа. |
| Масштабирование? | Сервис без состояния (справочник read-only), один воркер разбирает 1000 адресов меньше чем за 2 с; масштабируется репликами. Правки оператора хранятся в отдельной SQLite. |
| Польза для Jana Post? | Аналитика по городам и районам, автоматическая зона доставки по району, курьер видит подъезд и этаж без звонка, оператор правит только неуверенное. |
