# Безопасность

Как Jana Address защищён при локальном запуске и при встраивании между другими сервисами. Код: `src/jana_address/api/security.py`, тесты: `tests/test_security.py`.

## Коротко

* Сервис **не ходит в сеть** в рантайме: ни внешних API, ни телеметрии. Справочник и модель лежат в образе, образ собирается с `--network=none`. Через него нельзя достучаться до других систем (SSRF некуда направить).
* Принимает только JSON/JSONL с адресами; данные не исполняются, шаблонов и eval нет, SQL только с параметрами.
* По умолчанию `docker compose` слушает **только 127.0.0.1**; для доступа из сети включается **ключ доступа** (`JANA_API_KEY`).
* Запросы на изменение с чужого сайта отклоняются (`Origin`), чужие имена хоста отклоняются (`JANA_ALLOWED_HOSTS`, защита от DNS rebinding).

## Настройки

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `JANA_API_KEY` | пусто (API открыт) | ключ для `/api/*`: заголовок `X-API-Key: <ключ>` или `Authorization: Bearer <ключ>`. UI спрашивает ключ один раз и ставит cookie `HttpOnly; SameSite=Strict` (в cookie производный HMAC-токен, а не ключ). Без ключа открыты только `/api/v1/health` (healthcheck) и `/api/v1/auth` (вход) |
| `JANA_ALLOWED_HOSTS` | в образе пусто (любой), в compose `localhost,127.0.0.1,[::1],jana-address,*.trycloudflare.com` | допустимые значения заголовка `Host`, `*.домен` для поддоменов; остальное 400 |
| `JANA_ALLOWED_ORIGINS` | пусто | сайты, которым разрешено менять данные из браузера (`https://crm.example`); свой адрес сервиса разрешён всегда |
| `JANA_MAX_UPLOAD_MB` | 100 | лимит тела запроса; проверяется по `Content-Length` до чтения и по ходу чтения |

Ключ сравнивается за постоянное время (`hmac.compare_digest`). Генерировать длинным случайным: `python -c "import secrets; print(secrets.token_urlsafe(32))"`.

```bash
JANA_API_KEY=... docker compose up -d
curl -H "X-API-Key: $JANA_API_KEY" -F file=@sample_input.json http://localhost:8000/api/v1/parse/batch
```

## Что закрыто и как

| Угроза | Защита |
|---|---|
| Доступ к данным пакетов из локальной сети | compose публикует порт на `127.0.0.1`; при открытии наружу нужен `JANA_API_KEY` |
| CSRF: чужая страница в браузере оператора шлёт POST/PATCH/DELETE на localhost | запрос с `Origin`, не совпадающим с адресом сервиса, получает 403; cookie входа `SameSite=Strict` |
| DNS rebinding: чужой домен указывает на 127.0.0.1 и читает ответы | `JANA_ALLOWED_HOSTS`: чужой `Host` получает 400; с ключом у такой страницы нет cookie |
| SQL-инъекция | все значения пользователя передаются параметрами; в текст запроса подставляются только константы и сортировка из закрытого списка |
| Выход за папку при раздаче UI | путь нормализуется и проверяется, что он внутри `static/` |
| XSS в интерфейсе | React экранирует вывод, сырого HTML (`dangerouslySetInnerHTML`) нет; `X-Content-Type-Options: nosniff` |
| Встраивание UI в чужую страницу (clickjacking) | `X-Frame-Options: DENY` |
| Формулы в CSV-экспорте (адрес из чужой системы начинается с `=`, `+`, `-`, `@`) | в CSV такие значения начинаются с `'`; JSON-ответ не меняется |
| Огромный запрос, сверхглубокий JSON, число в тысячи цифр | 413 до чтения тела; 422 на вложенность и на число длиннее лимита Python |
| Долгий разбор одной строки | разбор линейный: адрес в 200 тыс. символов разбирается примерно за 1,3 с; `scripts/fuzz.py` гоняет инварианты на мусорном вводе |
| Запуск от root в контейнере | процесс работает под пользователем `app` (uid 10001), записывать может только в `/app/var` |
| Подмена зависимостей | версии зафиксированы в `requirements.txt`, колёса лежат в `vendor/wheels`, сборка без сети |

## Данные

* Батч `POST /api/v1/parse/batch` **ничего не хранит**: ответ отдаётся и забывается.
* Пакеты, загруженные через UI, лежат в `edits.sqlite` (том `jana-edits`) до удаления кнопкой в списке или `DELETE /api/v1/sessions/{id}`. Если в адресах бывают ФИО и телефоны, это персональные данные: том стоит удалять после работы (`docker compose down -v`) или не пользоваться UI-пакетами для таких данных.
* Адреса в сообщения логов не пишутся: при ошибке разбора пишется `id` записи и трассировка (в тексте исключения может оказаться фрагмент строки). Журнал доступа uvicorn пишет URL запроса, а в нём бывает поиск UI (`?q=`). Если логи уходят в общую систему, учитывать это или выключить журнал доступа (`--no-access-log`).

## Встраивание между сервисами

Рекомендуемая схема: сервис стоит во внутренней сети рядом с потребителями, наружу не публикуется.

1. Задать `JANA_API_KEY` (из секретов оркестратора, не в образе) и передавать его в `X-API-Key` из вызывающих сервисов.
2. Вызывать по имени сервиса (`http://jana-address:8000`) и добавить это имя в `JANA_ALLOWED_HOSTS`.
3. Если нужен доступ снаружи: TLS, лимит частоты запросов и журнал доступа на обратном прокси (nginx, Traefik, API-шлюз). В самом сервисе TLS и rate limiting нет намеренно: это задача прокси.
4. Батч stateless: можно запускать несколько реплик за балансировщиком; UI-сессии хранятся локально в SQLite, их держать на одной реплике.

## Ограничения (честно)

* Один общий ключ, без ролей и пользователей: все, у кого он есть, видят все UI-пакеты. Для нескольких команд нужен вход через корпоративный SSO на прокси.
* Нет ограничения частоты запросов: тяжёлый батч занимает процессор; ставить лимит на прокси.
* `/docs` и `/openapi.json` открыты без ключа: в них только описание API, данных нет.
* Ссылка cloudflared quick tunnel публичная: всё, что открыто без ключа, видно любому, у кого есть ссылка. Для демо друзьям это допустимо, для реальных данных включать `JANA_API_KEY`.
* Зависимости на известные уязвимости сканером не проверялись (в офлайн-окружении нет `pip-audit`); перед внедрением прогнать `pip-audit -r requirements.txt` и `npm audit` в `frontend/`.
